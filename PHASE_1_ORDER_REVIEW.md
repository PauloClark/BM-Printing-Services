# Phase 1: saved orders and staff review

## Scope and architecture

Inspected the existing checkout form, frontend order client, Supabase token verification and trusted role mapping, MongoDB order model, order/file routes, shared Staff/Admin orders component, and My Orders. Reused these features; no duplicate API, database table, authentication system, or order form was added.

Orders remain in MongoDB `bmprinting.orders`. Express is the active order API; Supabase supplies authentication, not order storage. The local API health check returned `db: connected`. No migration, SQL, or Supabase RLS change is required or applied.

- `src/components/Pages/StaffOrders.jsx`: labels the shared Staff/Admin section **Incoming Orders**.

- `server/routes/orderFiles.js`: applies the same ownership restriction to protected file access.
- `tests/orderOwnership.test.js`: regression coverage for mismatched owner IDs and safe error responses; legacy email-only fixtures now have no owner ID.
- `scripts/check-phase1-workflow.mjs`: focused real-browser/Express/MongoDB acceptance check that stops with Pending orders.
- This report. `dist/` was regenerated by the production build.

No Home, Products, carousel, Login/Register UI, role assignment, profile, Track Order UI, or unrelated stylesheet was edited.

## Identity, visibility, and details

The frontend sends the existing authenticated access token. Express verifies it with Supabase Auth and assigns `customerId` from the verified user, not the request's `userId` or `customerId`. It similarly binds email and forces new orders to Pending. Invalid supplied credentials cannot silently become guest checkout.

The existing record retains contact information, product/quantity, applicable size/color/dimensions in `specs`, original uploaded design metadata, notes, payment method, total, and server order time. Checkout reports success only after the record has been saved. My Orders reads the saved record through the authenticated customer API.

Staff and Admin share `StaffOrders`, which retrieves `/api/staff/orders` on opening, every five seconds, on focus, on Refresh, and after existing actions. New orders need no copying. View Order already displays the full saved information and uses authenticated file endpoints for preview/download. The backend independently verifies staff/admin roles from trusted `app_metadata.role`; editable profile fields do not grant access.

Customer order and file reads require the verified customer ID. Email compatibility remains only for old records with no assigned owner. Records already tied to a different ID are no longer exposed solely because their email matches. If historical accounts need linking, verify ownership and reconcile those records explicitly; no ownership migration was performed.

Failed creation returns a support reference and directs the customer to check My Orders before retrying. Detailed errors remain in backend logs, correlated with that reference. Raw database error messages are not returned to the browser.
